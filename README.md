# Smart Local Stock

Рабочий учебный MVP для моделирования локального хранения товаров в опорных ПВЗ (Anchor) и выбора логистического маршрута Hub/Mesh.

## Запуск (Windows / PowerShell)

```powershell
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
streamlit run app.py
```

При первом запуске схема SQLite создаётся автоматически. Для тестового набора используйте кнопку «Загрузить демонстрационные данные». Она добавляет только отсутствующие записи и не перезаписывает существующие товары, точки и остатки.

## Реализовано

- Каталог SKU и сеть точек (Anchor, обычные ПВЗ, Hub), включая создание новых точек.
- Отдельный выбор конкретного Anchor при размещении товара на локальном хранении.
- Приёмка товара на Anchor, обычный ПВЗ или Hub, резервы и журнал движений запасов.
- Демонстрационный кабинет продавца: создание поставки от продавца в Hub и подтверждение приёмки с автоматическим увеличением складского остатка.
- Создание заказов с проверкой доступных остатков.
- Реальная очередь Mesh-партий по паре Anchor → обычный ПВЗ.
- Подсчёт фактического числа заказов и суммарного объёма товаров в партии.
- Проверка целевой загрузки, ограничений 130 заказов / 1 500 л и максимального ожидания 5 часов.
- Сравнение стоимости Mesh по фактическому размеру партии с альтернативой Hub.
- Перевод партии на Hub, если Mesh экономически невыгоден; блокировка перевода, если на Hub недостаточно запаса.
- Отправка Mesh-партии и распределение стоимости рейса по заказам партии.
- Управление статусами, отмена заказов и возвраты.
- Диспетчер инцидентов: анализ текстового описания по правилам MVP, формирование плана действий и автоматическое переключение заказа Mesh в сценарный маршрут «Hub (обход)» для инцидента на пути. На карте перестраивается путь Anchor → Hub → ПВЗ; это модельная симуляция, не интеграция с диспетчерской RWB.
- Оперативный центр диспетчера: единый экран текущих заказов, запасов, резервов, партий, открытых инцидентов, возвратов, входящих поставок и расчётных финансов.
- Симулятор повседневной смены: по кнопке создаёт заданный поток заказов на основе фактических остатков Anchor, запускает правила Mesh/Hub, обрабатывает партии, переводит часть заказов через этапы «В пути» → «Готов к выдаче» → «Выдан», а по отдельному флажку создаёт дорожный инцидент для проверки обходного маршрута. Результаты смен сохраняются в SQLite.
- История симуляций с количеством созданных/не созданных заказов, отправками, прибытием, выдачей, инцидентами и расчётными затратами.
- Безопасная очистка временных данных симулятора в оперативном центре: удаляются только заказы смен `SHIFT-*` и связанные тестовые записи, складские движения откатываются; каталог, точки, настройки и ручные операции сохраняются.
- Полная финансовая модель Mesh/Hub: транспорт, переменные расходы, дополнительная выплата Anchor, пополнение, хранение и распределённая стоимость системы.
- Подробный финансовый аудит и пороги безубыточности: `docs/financial_audit.md`.
- 12-месячный прогноз с ростом спроса, долей Mesh, числом рейсов, сравнением с Hub, накопленным эффектом, ROI, NPV и безубыточной доплатой Anchor.
- Старт с 150-го дня создаёт синтетическую историю 150 дней: 6 000 выданных заказов, движения запасов, поставки продавца и дневную финансовую сводку. При текущих условиях (40 заказов/день и лимит ожидания 5 часов) поток остаётся на Hub, если Mesh не проходит полную экономику. Это модельная история, не реальные данные RWB.
- Расчётная финансовая сводка по заказам.
- Сценарный калькулятор экономики четырёх сторон: маркетплейс, владелец ПВЗ, продавец и покупатель; все вводимые тарифы помечены как гипотезы.
- Калькулятор пополнения Anchor по формулам доступного и целевого запаса; средний спрос D вводится оператором и не является ML-прогнозом.
- Автоматическая проверка ожидающих партий при каждом обращении к приложению (не фоновый планировщик).
- Оперативный центр обновляет панель смены каждые 2 секунды, пока она запущена и открыта. После закрытия приложения симуляция не продолжает работу.

## Интерактивная карта сети

- Отдельный раздел «Карта логистики» показывает региональный СЦ WB Казань (Зеленодольск), проектный Anchor и все пять демонстрационных городских ПВЗ Йошкар-Олы одновременно.
- Для выбранного заказа отображаются источник, ПВЗ назначения, дорожное расстояние и расчётное время (если доступен OSRM). После зарегистрированного дорожного инцидента показывается обход через Hub с двумя дорожными участками.
- Дорожная геометрия строится по открытой дорожной сети OpenStreetMap через OSRM; при недоступности сервиса карта показывает схему и не выдумывает километраж/ETA.
- Красный маркер транспорта перемещается по маршруту через ручной слайдер/шаги. Это демонстрационная симуляция, а не GPS-трекинг WB.
- СЦ Зеленодольск показан как подтверждённый объект WB; Anchor — проектная точка, городские ПВЗ — ориентиры для демонстрации, адреса и координаты требуют сверки по официальной карте WB.
- Карта использует pydeck, requests и требует доступа к картографическим тайлам и OSRM.

## Как работает очередь Mesh

1. Если в Anchor достаточно запаса и заказ укладывается в ограничения, товар резервируется, а заказ попадает в ожидающую партию.
2. Партия группируется по направлению Anchor → конкретный обычный ПВЗ.
3. При достижении целевой загрузки (по умолчанию 80 заказов), предела вместимости или истечении 5 часов система принимает решение.
4. Полная расчётная стоимость Mesh на заказ: стоимость рейса / фактическое число заказов + переменные расходы на заказ.
5. Если Mesh дешевле Hub, партия отправляется. Иначе заказы переводятся на Hub при наличии там необходимого запаса.
6. Если запаса Hub недостаточно для всех заказов партии, партия получает блокирующий статус; после пополнения Hub её можно проверить повторно.

5 часов — проектное ограничение ожидания партии, а не подтверждённый SLA RWB. Отдельный фоновый планировщик не используется: проверка выполняется при создании заказа, при каждом обращении/перерисовке приложения и по команде оператора в разделе «Партии Mesh».

## Данные и допущения

- Стоимость рейса, Hub и переменных расходов — гипотезы модели, не подтверждённая внутренняя себестоимость RWB.
- Целевая загрузка 80 заказов — проектное допущение; ограничения 130 заказов и 1 500 л — заданные параметры модели.
- Публичные тарифы продавца нельзя подменять внутренней себестоимостью логистики маркетплейса.
- Исторические заказы сохраняют свои рассчитанные затраты. Новая логика партий применяется к новым заказам.
- SQLite хранит локальные данные в `data/smart_local_stock.db`. Файл базы данных не следует удалять при обновлении кода.

Продавец «ООО «ТехноПоставка»» и контакт `demo@example.invalid` — вымышленные демонстрационные данные. Поставка в Hub увеличивает остаток только после отдельного подтверждения приёмки.

Непрерывная симуляция — демонстрационный генератор тестовой нагрузки, а не интеграция с реальными заказами, API, GPS или системами Wildberries. Случайные события нужны для демонстрации обработки исключений и не являются статистическим прогнозом. Он создаёт записи в той же базе, что и ручные операции, поэтому данные симуляции остаются в журнале и влияют на остатки/финансы. Запускай смену на тестовой базе или после проверки остатков; повторные запуски создают новые заказы и расходуют доступный товар.

Обработка инцидентов основана на прозрачных правилах и ключевых словах в категории/описании. Она не использует внешнюю LLM, не анализирует live traffic и не отправляет команды реальному перевозчику. Если заказ уже в пути по Mesh и описание указывает на дорожную проблему, MVP меняет маршрут на «Hub (обход)» и строит путь через Hub; в остальных случаях формирует план ручной проверки.

Подробности: `docs/assumptions.md`, `docs/formulas.md`, `docs/architecture.md`.

## Публикация

Для Streamlit Community Cloud укажите `app.py` как основной файл. Локальная SQLite-база не является надёжным постоянным хранилищем в облачной среде; для постоянной публичной эксплуатации потребуется внешняя БД. SQLite сохраняется для локального MVP в соответствии с выбранной архитектурой.
