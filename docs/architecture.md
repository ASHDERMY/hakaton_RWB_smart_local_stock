# Архитектура Smart Local Stock

## Слои приложения

Streamlit UI → расчётный слой `engine.py` → слой данных `database.py` → SQLite.

## Основные сущности

- `pickup_points` — Anchor, обычные ПВЗ и Hub; новые точки можно добавить из UI.
- `sellers` — продавцы, поставляющие товары в Hub.
- `supplier_deliveries` — входящие поставки продавцов, ожидающие приёмки или уже принятые.
- `operational_runs` — журнал запусков демонстрационной смены: объём тестовой нагрузки, обработанные заказы, инциденты и расчётные затраты.
- `products` — каталог SKU и объём единицы товара.
- `inventory` — физический остаток, резерв и поступление в пути.
- `orders` — заказы, статусы, источник, маршрут, оценка затрат и связь с партией.
- `mesh_batches` — ожидающие и отправленные партии для направления Anchor → конкретный обычный ПВЗ.
- `stock_movements` — журнал приёмки, резервирования, снятия резерва, отправки, поступления, выдачи и возврата.
- `returns` — возвраты и результат проверки состояния товара.
- `incidents` — логистические инциденты, сформированный план действий и признак изменения маршрута.
- `settings` — редактируемые параметры модели с классификацией и пояснениями.

## Жизненный цикл Mesh-заказа

1. При создании заказа проверяется доступность товара в Anchor.
2. При наличии запаса создаётся/используется ожидающая партия; товар резервируется.
3. Система считает реальное число заказов и суммарный объём партии.
4. При достижении целевой загрузки, лимита вместимости или 5 часов выполняется экономическое сравнение Mesh и Hub.
5. При выборе Mesh все заказы партии переводятся в статус «В пути», резерв списывается из Anchor, стоимость рейса распределяется по заказам.
6. При выборе Hub резервы переносятся из Anchor в Hub; дальнейшее движение обрабатывается стандартным жизненным циклом Hub-заказа.
7. При недостатке запаса на Hub партия блокируется, резервы Anchor сохраняются, оператор может пополнить Hub и повторить проверку.

## Сохранность данных и миграции

При запуске `init_db()` создаёт отсутствующие таблицы и добавляет новые столбцы в существующую SQLite-базу через миграционные проверки. Исторические заказы не переназначаются и не пересчитываются. Новые таблицы и поля добавляются без удаления существующих пользовательских данных.

## Границы MVP

SQLite предназначена для локальной разработки и демонстрации. Для постоянной облачной эксплуатации потребуется внешнее постоянное хранилище. Выбранная локальная архитектура SQLite сохраняется до отдельного согласования изменения.


## Оперативный центр и симуляция смены

Оперативный центр агрегирует данные из `orders`, `inventory`, `mesh_batches`, `incidents`, `returns`, `supplier_deliveries`, `pickup_points` и `operational_runs`. Отображаются статусы заказов, запасы/резервы/входящие поставки, низкие остатки, заблокированные партии, открытые происшествия, возвраты, маршруты и расчётные затраты.

Кнопка запуска смены выполняет демонстрационный сценарий:
1. Проверяет активные Anchor, товары, остатки и обычный ПВЗ назначения.
2. Создаёт тестовые заказы в пределах выбранной нагрузки, используя текущие остатки.
3. Запускает существующую логику принятия решения Mesh/Hub и обработку партий.
4. Переводит зарезервированные Hub-заказы в статус «В пути»; часть отправлений проводит через прибытие в ПВЗ и выдачу.
5. По отдельному флажку регистрирует дорожный инцидент для одного отправленного Mesh-заказа, чтобы проверить формирование плана и обход через Hub.
6. Сохраняет агрегат запуска в `operational_runs`; все созданные заказы и движения остаются в основных таблицах приложения.

Это воспроизводимая тестовая нагрузка, а не реальные заказы Wildberries. Она изменяет складские остатки, резервы и финансовые показатели, поэтому повторные запуски расходуют товар. Для демонстрации рекомендуется использовать копию базы или предварительно проверить остатки. Оперативный центр обновляет данные при открытии/перерисовке страницы; фоновый сбор телеметрии и интеграция с API RWB не реализованы.


## Непрерывная диспетчерская смена

Таблица `simulation_control` хранит состояние смены и номер такта; `simulation_events` — хронологию операций; `simulation_vehicle_progress` — прогресс виртуальных машин. Streamlit fragment выполняет один такт каждые 2 секунды только пока смена активна и пользователь держит приложение открытым.

Каждый такт моделирует генерацию заказа через стандартный движок выбора Mesh/Hub, проверку/закрытие партий, отправку Hub-резервов, движение транспорта, выдачу, вероятностные дорожные инциденты и возвраты. Поставки продавца автоматически поступают на Hub; при низком локальном запасе выполняется складское перемещение Hub → Anchor с двумя записями движения. Карта показывает несколько виртуальных машин по геометрии OSRM/OSM. Это не GPS и не реальный автопарк WB.
