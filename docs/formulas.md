# Формулы и правила модели

## Доступный остаток

`I_available = I + I_in - I_res`

где:
- `I` — физический остаток;
- `I_in` — подтверждённое поступление в пути;
- `I_res` — зарезервированный остаток.

## Целевой остаток и пополнение

`I_target = D × L + SS`

`Q = max(0, I_target - I_available)`

где `D` — средний спрос в день, `L` — срок пополнения в днях, `SS` — страховой запас. В интерфейсе доступен калькулятор потребности: оператор задаёт D, L и SS, система автоматически рассчитывает доступный остаток, целевой запас и Q. Исторический прогноз спроса и автоматическое создание заявки на пополнение пока не реализованы.

## Формирование реальной Mesh-партии

Партия формируется для конкретного направления Anchor → обычный ПВЗ. В неё попадают заказы, для которых в Anchor есть доступный товар.

`N_batch = count(активных заказов в партии)`

`V_batch = Σ(volume_SKU × quantity_order)`

Партия не должна превышать:
- `N_batch ≤ 130` заказов;
- `V_batch ≤ 1 500 л`.

Целевая загрузка по умолчанию — 80 заказов. Это триггер для проверки экономики, а не обязательное минимальное число заказов.

## Стоимость Mesh

`C_Mesh/order = C_trip / N_batch + C_variable/order`

`C_Mesh/batch = C_trip + N_batch × C_variable/order`

В расчёте используется фактическое число заказов в партии, а не условная плановая загрузка. Стоимость рейса распределяется равномерно по заказам. Переменные расходы учитываются на один заказ, а не на каждую товарную единицу.

## Стоимость Hub

`C_Hub/batch = N_batch × C_Hub/order`

`C_Hub/order` — редактируемая сравнительная гипотеза, не подтверждённая внутренняя себестоимость RWB.

## Условия закрытия партии

Партия проверяется, когда:
1. Достигнута целевая загрузка (по умолчанию 80 заказов);
2. Достигнут лимит вместимости (130 заказов или 1 500 л);
3. Истекло максимальное ожидание (5 часов).

После наступления одного из условий:
- если `C_Mesh/order < C_Hub/order`, партия отправляется Mesh;
- иначе заказы переводятся на Hub, если там достаточно доступного запаса для всей партии;
- если на Hub не хватает запаса, партия блокируется до пополнения и повторной проверки.

Если партия ещё не достигла ни одного условия, она продолжает ожидать. Отправка не должна превышать ограничения вместимости.

## Ограничения текущей финансовой модели

Сейчас оценивается транспортная часть Mesh/Hub по заказам. Полная экономика хранения, пополнения, стоимости капитала в запасе, возвратной логистики, потерь, вознаграждения Anchor и обычного ПВЗ, маржинального эффекта продавца и влияния на покупателя ещё не завершена. Эти статьи должны быть добавлены до итогового вывода о выгодности решения.


## Финансы непрерывной симуляции

Для каждого заказа транспортная оценка рассчитывается действующими правилами маршрутизации:
- Mesh: `C_Mesh/order = C_trip / N_batch + C_variable/order`;
- Hub: `C_Hub/order = C_Hub/order` из настроек модели.

Сводные логистические затраты — сумма `estimated_cost` активных и завершённых заказов. Перемещение товара Hub → Anchor и поставка продавца учитываются в складском журнале, но не получают выдуманную денежную стоимость: стоимость закупки, хранения, обработки, обратной логистики и компенсаций должна быть отдельно задана/подтверждена. Поэтому общий показатель не является полной прибылью или P&L.


## Комбинированный маршрут Anchor → несколько обычных ПВЗ

Планировщик группирует ожидающий локальный спрос нескольких ПВЗ в один рейс, если координаты точек заданы, добавление следующего ПВЗ не превышает допустимое географическое увеличение маршрута, а суммарные заказы и объём укладываются в лимиты.

Предварительная группировка использует расстояние по прямой (haversine), а не дорожный километраж. Для дорожной оценки требуется геометрия OSRM/OpenStreetMap.

`C_Mesh(route) = C_trip + N_route × C_variable/order`

`C_Mesh/order = C_Mesh(route) / N_route`

`C_Hub(route) = N_route × C_Hub/order`

Mesh рекомендуется, если расчётная стоимость ниже Hub. Текущая версия является планировщиком-рекомендателем: она не меняет статусы заказов, складские остатки и не запускает перевозку.
